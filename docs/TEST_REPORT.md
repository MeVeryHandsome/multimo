## 复现

```bash
scripts/demo.sh
```

脚本依次下载并校验测试数据、检查检测模型权重（Git LFS）、`docker compose up`、登记 `testdata/benchmark/corpus.json` 中的 223 个文件并等待处理完成（首次处理耗时较长，主要是约 300 个关键帧的 VLM 分析和 2361 个底图切片的向量化），然后运行评测并把报告保存到 `demo-output/`。服务已在运行时：

```bash
docker compose exec backend multimo testsuite
```

或调用 `POST /api/v1/testsuite/run`，在前端“评测”页查看进度和结果。

问答结果每次运行会有小幅波动，因为 VLM 回答和 Decision 打分不是完全确定的：P5 期间 4 次完整运行分别为 40、41、41、42 题正确（期间有代码改动，见调优记录），其中 qa50 在第一次运行中判错，单独重问时回答正确。检索结果在代码不变时是稳定的。

**模型是怎么来的**（训练命令、全部对比和试过但没有采用的方法见 [detector/README.md](../detector/README.md#模型)）：

1. 公开模型都是 640 输入训练的，对二三十像素宽的小目标分辨率不足。在 8×RTX 4090 服务器上以公开的 YOLO11x、YOLOv9e VisDrone 模型为起点，用 VisDrone train + test-dev 按 1280 输入微调（YOLO11x 再按 1536 继续训练）。第一次只用 train 训练时第 5 轮后就过拟合，按本口径没有收益，所以并入了 test-dev。
2. 每个模型按 1024 / 1280 / 1536 推理并融合；两个结构不同的模型再融合。同一模型的不同轮次互相融合没有收益，不同结构才有。
3. 拆解漏检的来源后发现，按平均分数取阈值时，大部分漏检的目标其实有正确的框，只是分数排在误检后面（第二轮 YOLO11x 三尺度：20.3% 的漏检中 12.3 个百分点属于这种情况）。于是加了一个重打分模型（梯度提升树），用每次推理各自的分数、检出次数、尺寸、位置、拥挤程度和同一位置上其他类别的框重新打分。

| 步骤（阈值都按标定集准确率 ≥ 86% 选） | 标定集漏检率 | 评测集 准确率 / 漏检率 |
| :--- | ---: | ---: |
| 公开 YOLOv9e，1024 | 23.9% | 87.2% / 26.7% |
| 微调 YOLO11x，1024 + 1280 + 1536 | 20.3% | 85.7% / 22.2% |
| 微调 YOLO11x + YOLOv9e，6 次推理平均分数 | 18.3% | 86.6% / 19.9% |
| 同上 + 重打分（部署） | 15.0% | 86.1% / 16.5% |

**评测集没有参与训练和选择**：模型轮次、推理组合、重打分模型和阈值都按 VisDrone val 中不属于评测集的 448 张图（标定集）上的结果选定。重打分模型只能在标定集上训练（其他标注数据都用来训练检测模型了），所以用 5 折交叉验证：标定集上的分数和阈值来自没见过该图的那一折，最终模型用全部标定集训练，在评测集上只算一次。只有一处参考了评测集：各候选按“标定集准确率 ≥ 85%”选阈值时，评测集准确率在 84.6%~85.7% 之间，有的低于要求，因此改为留 1 个百分点余量、按 86% 选。这一改动只会让漏检率更高。

上表最后一行是离线计算的；系统完整评测（本报告）得到 TP 2582、FP 418、FN 511，GPU 服务器上的检测服务经 HTTP 接口复测得到 TP 2580、FP 415、FN 513，三者相差不超过 3 个框（GPU 服务用半精度推理）。

**为什么还到不了 5%**：重打分模型只能在融合后平均分数 ≥ 0.10 的框里挑选；即使把这些框全部保留（准确率只剩 60.1%），评测集上仍有 10.3% 的可见目标没有任何候选框。所以在“类别一致”的口径下，5% 漏检既不是调阈值能达到的，也不是重打分能达到的，需要更强的检测模型。剩下的漏检集中在 people（召回率 60.3%）、带篷三轮车（33.8%）和三轮车、自行车、货车（60% 左右）：这些目标只有二三十像素宽、彼此外观相近，按大类匹配时漏检率是 11.6%。

### 空间对齐：DJI 飞行记录路径通过；无元数据的视觉定位中位误差 108 m，未达标

**有元数据**：DJI 视频按文件名时间与飞行记录对齐（自动识别出 UTC-8 时区偏移），51 个关键帧全部由飞行记录插值定位，存储坐标与独立插值结果一致（最大偏差 0.00 m）。这里的真值就是飞行记录本身，所以只作为流程验证。

**无元数据**：UAV-VisLoc 01 区 82 张照片，不提供 GPS，只给拍摄时间和同一区域的卫星底图（0.3 m 分辨率 GeoTIFF）。系统把照片与底图切片做图像向量匹配，按时间顺序做航迹平滑，再在选中位置附近做局部细化。

| 已定位 | 中位误差 | 平均误差 | P90 | <100 m | <250 m |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 82/82 | 108 m | 277 m | 770 m | 48.8% | 63.4% |

原因分析：前 30 个候选中有一个在 100 m 内的照片占 81.7%，但最终选中的只有 48.8%。瓶颈在于从候选中选对位置：照片和卫星图拍摄于不同年份和季节，农田、水面的外观差别大，图像向量的相似度区分不开相邻的相似地块。让 VLM 在候选中挑选、用 SIFT/ORB 做几何校验都试过，都没有改善（见调优记录）。

## 评测方法的修正

评测代码本身也有过几处修正，结果以修正后为准：

- **UAVDT 忽略区域**：UAVDT 为每段视频提供 `*_gt_ignore.txt`，标出车辆未标注的区域（M1004 第 1 帧有 3 块，占画面大半）。按数据集协议，落在这些区域的检测不计；原来没有读取，导致 M1004 的 23 个检测被算作误报。关键帧一致性 58.8% → 59.7%。
- **按类别的准确率和召回率**：原来按类别匹配时把其他类别的标注也算作漏检，召回率出现负数。改为每个类别的预测只与该类标注匹配。只影响明细表，主指标不变。
- **问答评分规则**：把 Decision 的评分说明写明确：只评判问题实际询问的内容；参考答案中标为“约”的人工计数允许 ±25%；超出问题范围的细节只有与参考答案矛盾时才扣分。实测对结果没有影响（同一批回答前后都是部分正确的仍是部分正确）。
- **坐标解析**：坐标题除“北纬/东经”写法外，也识别“纬度 33.7、经度 -118.3”这种带符号的写法。
- **检索准确率定义**：按要求定为前 10 名中的相关数 ÷ min(10, 相关总数)，即相关结果只有 1~2 个时，出现在前 10 名就算 100%。传统的 P@10 一并列出（0.356）。
