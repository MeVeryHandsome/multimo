## 处理流程

任务链：`ingest → keyframes → analyze → geo`；卫星底图另加 `basemap`，视觉定位的照片在航迹平滑后另加 `georefine`。每一步是 `tasks` 表里的一行，失败按退避重试，依赖未就绪时延后（不消耗重试次数）。

1. **接入（ingest）**：按文件头识别类型（视频 MP4/WMV/FLV/MOV/MKV/AVI，图像 PNG/JPEG/TIF，文档 PDF/DOC/DOCX/TXT/CSV/GeoJSON），读元数据（ffprobe、EXIF、GeoTIFF 地理参考），生成缩略图；文档抽文本、按页切块。
2. **关键帧（keyframes）**：
   - 视频按内容变化选帧：每秒 2 帧的 64×36 灰度签名，与上一关键帧差异超过 `KEYFRAME_CHANGE_THRESHOLD`（0.08）即取新帧；最小间隔 2 秒、最大间隔 15 秒、最多 60 帧。连续航拍没有镜头切换，ffmpeg 场景分数最高只有 0.012，所以不用场景检测。长视频只解码关键帧（466 秒 1080p 从 45 秒降到 13 秒）。
   - 图片和遥感影像各一帧；大幅 GeoTIFF 用自带读取器生成概览图。
   - 每帧计算多模态向量（`tongyi-embedding-vision-plus`，1152 维）；相邻视频关键帧相似度 ≥ 0.97 视为重复画面并丢弃。
3. **分析（analyze）**：
   - **目标框**：配置了检测服务（`DETECTOR_BASE_URL`，见 [detector/](../detector/README.md)）时，无人机照片（原图）和视频关键帧先送检测模型（VisDrone 训练的 YOLOv9e，10 类），框和计数以检测结果为准。检测服务不可用或未配置时，由 VLM 输出框（`bbox_2d` 为 0~1000 相对坐标，实测与像素标注吻合到 1~3 px）。遥感影像的类别（船只、储油罐、桥梁等）不在检测模型的类别中，仍由 VLM 画框。
   - **描述**：每帧一次 VLM 调用，返回 JSON：中文描述、场景标签、昼夜/天气/视角/高度、各类计数、地标、画面文字、地点猜测。有检测结果时，提示词中给出检测计数，VLM 不再输出框，描述中的数量与框一致；这一步从约 65 秒、4100 个输出 token 降到约 10 秒、260 个。
   - 框换算成关键帧像素坐标存入 `detections`（`source` 为 `detector` 或 `vlm`）。描述、标签、计数、地标、文字拼成检索文本并计算文本向量。VLM 不可用时用本地模板描述（尺寸、亮度、时间、位置），并标记待重跑。
4. **空间对齐（geo）**，按可靠性依次尝试：
   - 配套飞行记录（如 DJI CSV）：按整点时差把文件名上的本地时间对齐到日志的 UTC 时间（自动找到 UTC-8），逐关键帧插值出经纬度和高度。
   - EXIF / 视频容器里的 GPS。
   - VLM 读到的地名（置信度 ≥ 0.5）在 GeoJSON 地名库（Natural Earth，含中文名）里查城市级粗位置。
   - 视觉定位：素材登记时指定了参考底图（`geo_reference`），或粗位置落在某张底图范围内时，把关键帧中心正方形缩放到 448 px、做 12 个角度的旋转查询，与底图切块（250/300/400 m 三种尺度）的多模态向量比对，取前 30 个候选；同一集合的照片全部完成后，按拍摄时间用 Viterbi 做航迹平滑（相邻照片位移不超过 `GEO_MAX_SPEED_MPS × Δt`）。
   - 局部细化（georefine）：切块按半个边长的步长排列（125~200 m），选中的切块中心离真实位置仍可能有约 100 m。平滑后在选中位置 ±150 m 内按 50 m 网格、以选中切块的尺度截取底图，与照片比对，移到最相似的位置（`geo_source = visual-refined`）。
5. **底图索引（basemap）**：WGS84 地理参考、两个方向跨度都超过 1 km 的栅格，按三种尺度、半步长切块并计算多模态向量（UAV-VisLoc 01 区约 2000 块）。

### 视觉定位的实测依据（UAV-VisLoc 01 区，82 张无 GPS 照片）

| 方案 | 中位误差 | <100 m | <250 m |
| :--- | ---: | ---: | ---: |
| 单张检索，4 个旋转，300 m 切块 | 472 m | 28% | 40% |
| + 航迹平滑 | 232 m | 32% | 51% |
| 12 个旋转 + 三种尺度 + 航迹平滑（Python 原型，448 px） | 128 m | 48% | 62% |
| 服务实现，512 px 输入 + 航迹平滑（P3） | 129 m | 40% | 57% |
| 服务实现，448 px 输入 + 航迹平滑 | 129 m | 46% | 62% |
| 服务实现，448 px + 航迹平滑 + 局部细化（当前） | 108 m | 49% | 63% |

- 切块尺度用 5 张不在评测集里的照片标定。最大速度 25 m/s 是事先定的默认值，15 和 40 也试过，25 最好，所以这一项在评测集上有轻微的调参成分。
- 试过 SIFT/ORB + RANSAC 做几何校验：即使在真实位置，内点也只有 5~9 个（照片和卫星图拍摄年份、季节不同），无法使用，已放弃。
- 失败的主要是纯江面照片，单张无法定位。
- 前 30 个候选中有一个在 100 m 内的照片占 82%，最终选中的不到一半：瓶颈在候选选择。让 VLM 在前 6 个候选中挑选也试过（<100 m 38%，低于航迹平滑的 40%），没有采用。详见 [测试报告](TEST_REPORT.md#调优记录)。

## 模型分工

| 模型 | 接口 | 用途 |
| :--- | :--- | :--- |
| `qwen3.8-max` | OpenAI 兼容 `chat/completions`，支持图像输入 | 关键帧描述、地标识别、答案生成；未配置检测服务时也画目标框 |
| `visdrone-yolov9e` | 自带检测服务 `POST {DETECTOR_BASE_URL}/v1/detect` | 无人机照片和视频关键帧的目标框（VisDrone 10 类） |
| `text-embedding-v4` | OpenAI 兼容 `embeddings`，1024 维 | 关键帧描述与文档片段的向量 |
| `tongyi-embedding-vision-plus-2026-03-06` | DashScope 原生 `multimodal-embedding`，1152 维，每批 4 张 | 关键帧图像向量、底图切块、视觉定位、以文搜图 |
| `vllm-sr/d3-ultra` | `POST https://app.vllm-sr.ai/v1/systemone`，与下述 decisions 格式相同 | 意图分类、证据相关性打分、问答裁判 |

Decision 模型只做判断和打分，不生成文本；该模型的 `chat/completions` 通道在网关上不可用（返回 `model_not_found`）。

### Decision 接口约定（2026-11-02 实测）

> 2026-11-03：原服务商（bamboonode `startlux-decision-27b-autothink`）自 14:16 起持续返回 HTTP 500，改用 `vllm-sr/d3-ultra`（`/v1/systemone`）。请求和返回格式与下面一致，实测 choice/score 中文题判断正确，单次约 0.5 秒。

```http
POST {DECISION_BASE_URL}/decisions
Authorization: Bearer <DECISION_API_KEY>

{
  "model": "startlux-decision-27b-autothink",
  "state": "背景信息，纯文本",
  "questions": {
    "<id>": { "type": "choice", "instructions": "问题", "criteria": {"<选项id>": "选项描述", ...} },
    "<id>": { "type": "score",  "instructions": "评分要求", "criteria": ["等级0描述", "等级1描述", ...] },
    "<id>": { "type": "noul",   "instructions": "..." }
  }
}
```

- 一次请求可以带多个问题。
- `choice`：criteria 可以是对象或数组。返回 `choice`、`confidence`、`probabilities`、`none_probability`。
- `score`：criteria 需要 2 到 10 个等级。返回 `score`（按概率加权的期望分）、`probabilities`、`legend`。
- `noul`：返回一个 0 到 1 的数，含义未确认，系统中不使用。
- 返回的 `usage` 里有 `input_tokens` / `output_tokens`。

## AI 网关（`internal/pkg/llm`）

- 统一封装三类调用：chat（含图像，支持 JSON 模式）、embedding、decision。
- 每个端点有独立的并发上限（`*_MAX_CONCURRENCY`）。
- 每次调用最多尝试 `1 + AI_MAX_RETRIES` 次：网络错误、超时、429、5xx 按指数退避加抖动重试，429 优先遵循 `Retry-After`；其他 4xx 不重试；JSON 模式下回复里没有 JSON 对象也会重试。
- 全部失败后按 `AI_FALLBACK_ENABLED` 走本地兜底，调用日志里状态记为 `fallback`：
  - embedding：本地特征哈希向量，模型名 `local-hash-v1`。一批向量不会混用两种来源，入库时记录模型名，只和同一模型的向量比较。
  - decision：按关键词重合度判断。
  - chat：由调用方提供兜底函数。P3 计划给关键帧描述配"元数据 + 颜色亮度统计"的模板描述；目标检测兜底返回空结果，并把该帧标记为待重跑。
- 每次调用写一条 `ai_call_log`：端点、模型、用途、token 用量、延迟、尝试次数、状态、输入输出摘要（截断到 `AI_LOG_PAYLOAD_CHARS`）。图片只记尺寸和大小，API key 不进日志。`GET /api/v1/system/ai-calls` 汇总查看。
- 实测（2026-11-03）：`qwen3.8-max` 支持图像输入和 JSON 模式，关闭思考（`enable_thinking=false`）后单张图描述约 5～8 秒；`text-embedding-v4` 约 0.6 秒；Decision 约 0.5 秒。

## 数据模型要点

- 图片和遥感影像在 `keyframes` 表里各占一行（`idx = 0`），和视频关键帧放在一起，检索、检测、问答只面对一种画面单元。
- 大幅 GeoTIFF（如 UAV-VisLoc 卫星图，9774×26762，805 MB）用自带的 `internal/pkg/geotiff` 读取：只解析文件头即可得到经纬度范围，缩略图只读采样到的像素行（约 0.02 秒）。ffmpeg 会把这种分块 TIFF 渲染成全黑，而且要读完整个文件。
- 任务队列存放在 `tasks` 表，用 `FOR UPDATE SKIP LOCKED` 领取，重启后自动恢复；临时错误按退避重试，永久错误直接标记失败。

## 混合检索（`POST /api/v1/search`）

检索单元是关键帧（含图片、遥感影像的单帧）和文档片段。

1. **查询理解**：规则解析经纬度、半径、纬度区间、"以东/以西"、日期和时间段；查询同时提到地名和画面（拍摄、视频、图像…）时，再让 VLM 提取拍摄地点，先查地名库，查不到才用模型估计的坐标（结果里标注来源 `gazetteer` / `llm-estimate`）。"美国小型无人机的高度限制"里的"美国"是法规适用范围，不会变成拍摄地点过滤。
2. **五路召回**（每路取前 100，均套用集合、类型和时空过滤）：
   - BM25：内存倒排索引，中文按单字 + 双字切分、英文按词；PostgreSQL 没有中文分词，也没有 BM25 打分，所以不用 tsvector。索引在关键帧或文档文本变化时自动重建。
   - 文本向量：`text-embedding-v4` 对关键帧检索文本和文档片段。
   - 以文搜图：`tongyi-embedding-vision-plus` 的文本向量对关键帧图像向量。
   - 目标计数：从查询中识别目标类别、数量下限（"20 人以上"）和否定（"几乎看不到小汽车"），按 VLM 给出的每帧计数筛选排序。
3. **融合**：按信号、按单元类型分别排名后做 RRF（k=60）。
4. **精排**：前 50 个候选交给 Decision 模型逐条判断是否满足检索需求（一次请求，约 1.2 秒），得分 = 0.8 × 相关概率 + 0.2 × 归一化 RRF，概率 ≥ 0.5 记为相关。带时空过滤的查询跳过这一步：候选文本里没有坐标，模型无法判断，而过滤条件本身已保证满足要求。
   - **空间过滤考虑定位误差**：视觉定位的坐标只准到一两百米，硬边界会漏掉拍在区域边缘的照片。每个关键帧带有定位精度（`geo_accuracy_m`：飞行记录约 5 m，视觉定位 125~200 m），位于边界外但在其精度范围内（最多 300 m）的结果也会返回，排在区域内的结果之后，不标为相关，并在 `signals.spatialDepthM` 中给出到边界的距离。
   - 只含地点的查询（"以某点为中心半径 300 米内拍摄的图像"，去掉坐标、半径和"拍摄的航拍图像"之类的词后没有其他内容）按到中心的距离排序；带其他内容的按文本相关度排序。
5. 默认按素材聚合，每个素材保留得分最高的单元。

## 智能问答（`POST /api/v1/qa`）

1. **点名素材**：从问题中提取文件名片段（`uav0000086_00000_v`、`P6519`、`01_0101.JPG`、"Palos Verdes"），匹配素材，给出素材摘要（时间、位置及来源、飞行记录统计、各类目标数量最大值）和代表性关键帧。
2. **Decision 判断问题类型**（文档 / 画面内容 / 位置 / 拍摄参数 / 跨来源），决定检索范围：文档题只查文档，跨来源题文档和素材都查。文档题和跨来源题还会让 VLM 把问题改写成中英文关键词各一条再检索，因为法规有中文也有英文，BM25 不能跨语言匹配。点名的文档单独在该文档内检索。
3. **Decision 判断证据是否有用**，保留有用的证据，至少保留最好的 4 条。
4. **VLM 作答**：只能依据编号证据回答，画面类问题附关键帧图片，句末标注引用编号；证据不足时明确说无法确定。VLM 不可用时返回最相关证据的原文。

## 前端（`multimo-frontend`）

React + Tailwind，静态文件由 nginx 提供，`/api` 反向代理到后端。视觉方向取自航空图：图上叠印的品红色标记模型给出的内容（检测框、引用编号），蓝色标记地理信息；数字和坐标用 Barlow Condensed 等宽数字，字体随前端打包，不依赖 Google Fonts（国内无法访问）。

| 页面 | 内容 |
| :--- | :--- |
| 素材 | 按类型、集合、文件名筛选；上传；处理状态自动刷新 |
| 素材详情 | 关键帧画面叠加检测框（可按类别开关）、视频时间轴上的关键帧条、位置读数（度分秒、误差、定位方式）、小地图（飞行轨迹、底图叠加）、描述与计数；文档可在文内检索 |
| 检索 | 自然语言查询；显示系统如何理解查询（坐标、范围、时间、目标数量条件）；按素材或按单元查看结果，悬停分数查看各路召回名次 |
| 问答 | 带引用编号的答案，引用链接到右侧证据（关键帧图片、文档页码） |
| 地图 | 全部已定位关键帧，按定位方式着色；卫星底图按地理范围叠加；可选在线瓦片（`MAP_TILE_URL`，内网填 `none`） |
| 评测 | 运行评测、查看进度、最近一次的指标对照和历史报告 |

## 评测（`internal/service/testsuite`）

标准答案全部来自数据集的人工标注、GPS 记录或文档原文，不用本系统的模型输出生成，避免自己评自己。评测集由 `scripts/lib/build_benchmark.py` 生成，说明见 [testdata/benchmark/README.md](../testdata/benchmark/README.md)。

| 指标（目标） | 数据 | 计算方式 |
| :--- | :--- | :--- |
| 数据类型（≥3 种） | 评测语料 223 个文件 | 解析成功（状态 ready）的类型数和格式数 |
| 关键帧自动标注一致性（≥40%） | VisDrone2019-VID val 4 段 + UAVDT 2 段，逐帧标注 | 关键帧上的 VLM 检测框换算回原始帧坐标，与该帧可见标注按 IoU≥0.5、同大类贪心匹配，F1 = 2TP/(2TP+FP+FN)；UAVDT 只标注车辆，其他类别不计。另给类别集合 Jaccard 和文本向量余弦作为语义一致性参考 |
| 目标识别准确率（≥85%）/ 漏检率（≤5%） | VisDrone2019-DET val 每 5 张取 1 张，共 100 张 | 与可见标注（面积≥600 像素、非重度遮挡）按 IoU≥0.5、类别一致匹配；与不可见标注或忽略区域重合的预测不计（VisDrone/COCO 惯例）。准确率 = TP/(TP+FP)，漏检率 = FN/(TP+FN)；同时给出按大类匹配和不排除不可见目标的结果 |
| 空间对齐（<100 m） | UAV-VisLoc 01 区 82 张（无 GPS，只给拍摄时间和参考底图）；DJI 视频 + 飞行记录 | VisLoc：系统推算坐标与 CSV 真值的 haversine 误差，看中位数，未定位按失败计入 <100 m 比例；DJI：关键帧坐标与独立插值飞行记录的偏差（流程验证） |
| 检索准确率（≥85%）/ 查全率（≥80%） | 50 条 query | 按素材聚合。准确率 = 前 10 名中的相关数 ÷ min(10, 相关总数)；查全率 = 前 max(10, 相关总数) 名中的相关数 ÷ 相关总数；50 条取平均。另给 P@5、P@10、R@5、R@10 和系统判为相关的结果集合的精确率/查全率 |
| 问答准确率（≥80%） | 50 个问答对 | 坐标题按回答中经纬度与真值的距离判定（≤ 容差）；其余由 Decision 模型按 0/1/2 打分，期望分 ≥1.5 为正确。评分规则：只评判问题实际询问的内容；参考答案中标为“约”的人工计数允许 ±25%；超出问题范围的细节只有与参考答案矛盾时才扣分 |

运行方式：

```bash
multimo testsuite                       # 全部 6 项，报告写到 DATA_DIR/reports/<时间>/
```

```bash
multimo testsuite -only retrieval,qa -out ./report -c 4
```

```bash
multimo testsuite -register             # 先登记 benchmark/corpus.json 并在本进程处理完队列
```

HTTP 接口：`POST /api/v1/testsuite/run`（后台运行，`sections` 可选）、`GET /api/v1/testsuite/status`、`GET /api/v1/testsuite/reports`、`GET /api/v1/testsuite/reports/{id|latest}`（JSON）、`GET /api/v1/testsuite/reports/{id}/{html|md|json}`（文件）。

每次运行输出 `test_report.json`（全部明细）、`test_report.html`（自包含页面，标注每项是否达标，含逐条 query / 问答 / 照片明细）和 `test_report.md`（摘要表和未达标明细）。实测结果见 [TEST_REPORT.md](TEST_REPORT.md)。
